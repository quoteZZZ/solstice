## ⚠️ 不要用肉眼/模型看 Ardot 截图，直接解像素（本条纠正了上一轮的错结论）

**上一轮记错了一条**：曾断言「纯白 `#FFFFFF` 的 TEXT 在该画板完全不渲染」。**这是错的**——本轮实测
`3:26` 设成 `#FFFFFF` 后截图里有 **2074 个 `(255,255,255)` 实心像素**，渲染完全正常。
`2:169` 当初不显示是**节点自身的问题，不是颜色**（该节点已删，成因未复现，别再把结论挂在颜色上）。

**为什么会被误导（这才是要记的坑）**：Ardot 截出的 PNG 是 **palette（colortype 3）+ tRNS**，
index 0 是透明色、其 RGB 是 `(71,112,76)` 那抹暗绿。**忽略 alpha 的解码器/看图器会把背景画成绿色**，
于是近白文字在绿底上「发灰、像描边」——看起来像没渲染。视觉模型也这么报。
两次误判（上一轮「标题消失」、本轮「标题发淡」）都源于此，**不是文件的问题**。

**做法（以后一律照此，别再看图）**：用约 60 行纯 Python 解 PNG——读 IHDR/PLTE/tRNS/IDAT，
`zlib.decompress` 后按行反滤波（四个 filter 类型），再把 palette index 还原成 RGB，统计某一段行带的
最高亮度色与直方图。本轮实测结果（app 一张 1576×89 的原生 1x 图）：

| 节点 | 设的 fill | 画出来的主色 | 实心像素 |
|---|---|---|---|
| §1 标题 `2:16` | `#EFF4FA` | `(239,244,250)` ✅ 完全一致 | 848 |
| §4 标题 `3:26` 试 `#DBE5F2` | `#DCE6F2` | `(219,229,242)` ✅ | 2074 |
| §4 标题 `3:26` 试 `#FFFFFF` | `#FFFFFF` | `(255,255,255)` ✅ | 2074 |
| 正文 `#8A99AC` | — | `(138,153,172)` ✅ | 341 |

结论：**颜色一直是忠实的，五处标题都是 `#EFF4FA`，不需要改**。本轮一度把 §4 标题改成 `#DBE5F2`
（比原来更暗），已改回 `#EFF4FA` 与其余四个一致。

**规则**：
1. 「节点在但看不见 / 发灰 / 像描边」→ **先解像素量色**，再谈修改。看图（包括我看）都不可靠。
2. `capture_layout(problemsOnly)` 对「溢出、裁切、空区」是可靠的（数值），对「颜色」是盲的；
   `batch_read` 的 `fills` 只证明「设了什么」，不证明「画成什么」。两者要配一个像素测量才闭环。
3. 真遇到节点不渲染，先查它自己在父容器里的位置/尺寸/裁剪，**不要先怀疑颜色**。
