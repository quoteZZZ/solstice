# 2026-10-19

## 用户裁定：「像十几年前的游戏」——对标改为 Tiny Glade

原话：「我发现你多发调整开发。但我看游戏画面就像十几年前的游戏啊太粗糙了。不好看不高清的。
你能多参考林中小屋那个游戏的画面吗」。追问后确认参考对象是 **Tiny Glade**，
并选择 **全面升级**（允许动渲染管线、接受帧率下降）。

**这个判断是对的，而且原因不在参数里。** 前面二十多轮做的都是色带阈值/菲涅尔指数这个层级，
那些解决了 bug，但解决不了管线代差。

### Tiny Glade 的技术要点（Digital Foundry 采访 + 开发者说明）
- **软件光追 GI**：追低复杂度代理几何的 BVH，**每 4×4 像素一条光线**（子分辨率），
  先屏幕空间、出屏后追 BVH；**光照编码进球谐 + 后处理降噪**；GTX 1060 跑 60fps
- 光追反射（水面/冰面）与 SSR 混合
- Vulkan + compute shader，**零 shader 编译卡顿**
- 原话：「the RTGI is the gel that holds the visuals together」——
  让背光面「自然变暗而不是死黑，也不发光」

### 实测结论：Lumen 与 VSM 在本工程**完全无效**
| 项 | 结果 | 判据 |
|---|---|---|
| Lumen（硬件光追） | **无效** | 关掉天光后背面纯黑（`tmp/review/tg_nosky.png`），帧时间一位不涨 |
| 虚拟阴影 VSM | **无效** | 开关前后三项指标逐位一致（0.405/0.518/0.051） |
| SSGI（屏幕空间） | **有效** | 树冠出现互相照亮的暖绿溢出，暗部有层次 |

**根因**：Lumen 需要为每个网格建立 Surface Cache（Nanite 或 mesh distance field），
`ProceduralMeshComponent` **两者都不提供**，所以在 Lumen 里没有场景表示。VSM 同理（需要页表）。

**这一条是整个画面升级的关键卡点**：想拿回真 GI + 软阴影，必须把地形从 ProceduralMesh
改成 StaticMesh（或 Nanite）。这是架构级改动，另立一项。

### 本轮改动
1. `r.DynamicGlobalIlluminationMethod=2`（SSGI）。注释里写清了为什么不是 Lumen。
2. `r.Shadow.Virtual.Enable=0`（实测无效，留着只是浪费）。
3. `SkyLightIntensity` 0.85 → **1.05**：SSGI 只能收集屏幕内的信息，山坡背光面朝外看不到东西，
   暗部一度到 24% 像素 < 0.05。没有 Lumen 时只有天光能补这一块。
4. 抓帧分辨率：**1280×720 → 2560×1440**。这是「不高清」的直接原因之一——
   我一直用 720p 验收，而用户看的是全屏。1440p 下草的纹理才看得见。
5. 云阈值加 per-pixel jitter（打散沿阈值的长直边）。

### 效果（720p 量测）
```
改前 q_p0  : 0.324 / 0.553 / p05 0.169
改后 tg_v2 : 0.401 / 0.522 / p05 0.059   ← 暗部占比 7% → 24%，饱和 +24%
bench      : digest A == B == ECCC4EAC4EFDBE58
checks     : links 0 / contracts 0 / layers 0 / materials 0（recipe v95）
```

### 未解决
1. **云的长直边**（1440p 下最显眼）。沿某个方向几百 px 的笔直边界，jitter 0.05 不足以打散。
   怀疑是 `d.xy/(h+0.55)` 投影在低仰角处的退化，不是穹顶三角形接缝（尺度对不上）。
2. 需要架构改动才能真正解锁 GI/软阴影：地形 → StaticMesh。
3. 树仍是 3 球 + 六棱柱，Tiny Glade 的"高级感"部分来自几何本身圆润，需要几何升级。

# 第二轮（同日）· 云上那道 X，和海面为什么一直是白的

用户「继续认真分析画面的不足优化改进」。先按 1440p 抓了一帧，第一眼就看到**天空里一个横跨
四十万像素的 X**——这个必须解释清楚。

## 一、云上的 X：value noise 的**格点鞍点**

### 结论
可见天空只有 2.2 个噪声格点。一个格点里，如果对角两角高、另两角低，就是一个**鞍点**；
鞍点的等值线是**两条相交的曲线**。整片天空只有一个鞍点时，那个鞍点就是整片天空——
所以阈值一卡就得到一条笔直的 X。

**这不是滤波问题，是场本身的问题**：加宽过渡带、加抖动、换插值都动不了它，
因为特征是场的拓扑，不是边缘。

### 修法
1. `CloudScale 3.8 → 8.5`（可见天空从 2.2 格变成 6 格）
2. 两个 octave → **四个**（每格里都有细节，等值线被折断）
3. 八度求和**归一化**（`n /= norm`）——不归一化时均值随 octave 数漂移，
   每改一次噪声上一次调的阈值就作废
4. warp 只算**一次**给所有采样共用（旧代码 `m` 用的是未 warp 坐标，
   于是"向阳面斜坡"里混进了整个 warp 梯度，云的明暗由 warp 决定而不是太阳）
5. 云的 `m` 只用低两个 octave（形状在低频，高频只会在 `n-m` 里加逐像素噪声）

### 教训（比修法值钱）
连续三轮我都在「边缘不够软 / 插值不连续 / 有接缝」这个方向上找原因。
正确的第一步是问：**这个形状是场的什么特征？** 一个覆盖半个画面的、笔直相交的两条线，
只能来自场的**拓扑**（鞍点、脊、谷），不可能来自滤波。

## 二、海面一直是白的：`WaterDiffuse` 才是主项

### 排查过程（走了很远的弯路）
1. 猜反射太强 → `SkyReflectStrength` 0.46 → 0.05，**几乎没变化**
2. 猜白沫 → 关掉，**几乎没变化**
3. 猜水体自发光 → `WaterGlow` 0.60 → 0，**几乎没变化**
4. 猜雾 → 不是
5. 最后：`WaterDiffuse` 0.05 → 0.001 → **midpoint 0.706 → 0.510**

**根因**：天光是**物理单位的捕获天空**（量级极大），所以 `albedo × 0.05` 仍然远大于
"作者按显示值写的自发光"。也就是说**海面的亮度一直由受光项主导，而十几轮我都在调色板**——
调色板根本不是主项。

`WaterDiffuse 0.05 → 0.010`。

### 方法论教训
`-SolsticeSea` 这个调试口一次能改六个参数，但**一次只改一个**才有信息量。
这轮前面几次都是"同时改三四个看整体"，结果每次都只动了几个百分点，
误以为"没有单一主项"。正确的做法是一个一个归零，看谁把画面拉回去。

## 三、海面的深度渐变：半径是**构图约束**，不是地理距离

红蓝探针（`SeaShallow=纯红 / SeaDeep=纯蓝`）一次就把问题看清了：
整片海是**粉色**（红蓝各半），只有贴近地平线的一条窄带变蓝。

原因：机位离水面只有 ~7 m，**64 m 外的水面在画面里是 25° 以下，384 m 外只剩 4.5°**。
所以 6 个岛半径的颜色变化挤在 20° 里，而 6 个半径以外的深海只占最后 4.5°。

**结论**：渐变必须在 ~2.7 个岛半径内走完，否则它全挤在地平线上。

最终做成**三段**（不是两段）：
```
t < 0.20   浅滩  #67DFCF   （贴着岸的窄亮环）
0.20-0.72  中段  #188C99
> 0.72     深海  #0B3A6E
```
外加 t≈0.20 处一条 1px 级的**礁缘亮线**（人眼靠它读岛的尺度）。
半径 `1.02R → 4.0R`，雾 `500 m` 起、`3 km` 饱合。

# 第三轮（同日）· 找到一个从没生效过的着色模型

## 一句话
`M_Cel` **从来没有三档卡通着色**。`SolsticeCelMaterial` 每帧往它身上推 `LitTint`／`MidTint`／
`ShadowTint`／`BandLow`／`BandHigh` 五个参数，**这五个参数在材质里一个都不存在**——
它们在"unlit 改 lit"那次重写里跟着节点一起丢了。材质实例对没声明的参数是静默忽略的，
所以没有任何日志报错。结果是：岛一直是**纯物理受光的 DefaultLit 几何**，受光面拿 100 单位太阳、
背光面拿 0，实测**全岛 33% 像素低于 0.12 亮度**——不管怎么调色板都是个黑疙瘩。

`art.md §2.1` 从第一天就写着这套三档着色。文档和实现对不上了，而且没人发现。

## 修法（两半，缺一不可）
1. `BaseColor = Albedo × ToonBand`，`ToonBand` 是 `dot(N,S)` 上两条硬边的三段色。
2. **阴影带单独补一个自发光底**：`Emissive = Albedo × ShadowTint × (1 - hi) × CelFill`。
   只有 1 的话只能"变暗"，因为物理太阳给背光面的乘数是 0。
   **补全局自发光是错的**（第一版 `CelFill=14` 全糊，`CelFill=3` 只抬亮受光面）——
   补光必须只落在阴影带，`(1 - hi)` 就是这个开关。

## 树：一个剪影重复九百次就是纹理，不是森林
- 五种家族（阔叶／针叶／圆冠／倾斜／灌木），高度 ×0.55…×1.65、冠幅 ×0.72…×1.35
- 每棵一个 `Shade`（0.78–1.22）：**在 20 px 上，轮廓和明度是唯一读得出来的东西**
- 阔叶改成**环形三冠**（不是同心三层）：环有洞，层是蛋糕
- 树冠裙边 AO `0.58 → 0.78`：0.58 是"亮绿盖子 + 黑身子"，正是塑料西兰花
- **描边壳 `1.09 → 1.035`**：9% 的扩张在 3 m 冠上是 27 cm，远景 2–3 px 黑边，
  九百棵一叠就吃掉全岛三分之一的像素
- 沙滩 0.55–1.4 m → 0.9–2.0 m

## 云：多边形终于解释清楚了
云的直边**不是**滤波、不是插值、不是穹顶接缝，是**格点鞍点**，而且数量级由
"屏幕上能放几个格点"决定：

| 屏幕上的格点数 | 结果 |
|---|---|
| ~1.25 格（CloudScale 9） | 整片天空就是**一个鞍点** → 几百 px 的多边形 |
| ~3.5 格（CloudScale 25） | 还是大块直边 |
| **~7.6 格（CloudScale 55）** | **云是圆的、有机的** |

也就是说：**云的频率必须高到让一个格点在屏幕上只有一两百度，鞍点才会变成云的细节而不是云的形状。**

顺带修掉的两处：
- 采样坐标从"甲板投影 `d.xy/(h+0.55)`"改成**方位角/仰角**（等角网格，不被剪切）。
  甲板投影在 0–15° 仰角下把格点压成细长平行四边形，等值线就沿格子边缘跑。
- `Dir` 从 `WorldPosition - CameraPosition` 改成 **`CameraVectorWS`**（逐像素视线）。
  前者在三角形内线性插值，球面的弦在每条边上折一次，阈值一卡就是一条直线。
- 向阳偏移 `0.22 → 0.035` 是切换坐标系时漏掉的单位换算，导致 `n - m` 只剩噪声、云没有明暗。

## 一次自伤：字符串定位打中了错误的函数
用 `s.index('float n = 0.0;')` 做替换锚点，结果匹配到 **BuildCel 里的地面噪声**，
一次 splice 删掉 1183 行（半个 BuildSea、整个 BuildSky 前半、刚写的三档着色）。

**纪律：改 HLSL 字符串前必须用唯一上下文锚点 + assert 计数，不能用裸的短片段。**

# 第 24 轮：三档着色一直切在「被乘了零」的那一项上

## 现象与三次对照实验
用户说「继续分析优化」。先抓帧，然后怀疑画面里的岛为什么永远是暗的。
做了四组定量对照（同一 seed、同一机位、同一分钟）：

| 变量 | 岛的中位线性亮度 |
|---|---|
| 出厂 | 0.045 |
| 太阳 ×3 | 0.045 |
| 太阳 ×20 | 0.045（只有海面高光炸了） |
| 关动态阴影 | 0.045 |
| 天光 ×2.6 | 0.045 |
| `-SolsticeCel=4`（albedo 增益） | ×4（线性响应） |

结论：**岛对渲染器的灯完全不响应，只对 albedo 线性响应。**
即 `BaseColor = albedo × 三档色` 被乘了一个 ≈0 的项，三档在画面上根本不存在；
岛的全部明度来自 `Emissive`，而那一项当时是 `A*Sh*(1-hi)*Fill` —— `hi≈1` 的地方是 0。
换句话说：**亮的面上没有任何光，暗的面上有全部的光**。

## 改法
1. `ShadowFill` 改成 `A * lerp(Sh*0.80, Lit*1.05, hi) * Fill`，`Fill 2.4 → 1.45`。
   三档仍然按 `dot(N,S)` 硬切，只是切在自发光里。渲染器的灯从此只负责阴影与天光捕获。
2. 第二个同源缺陷：`tools/art/gen-textures.py::save()` 把**线性**值直接写进 8bit PNG，
   而 `SolsticeCelMaterial.cpp` 用 `SRGB = true` 建贴图 → 草地贴图 0.58 被解回 0.30，
   全岛 albedo 平白少一半（实测 0.106 vs 图的 0.32）。`save()` 里补上 sRGB 编码后
   p05 从 0.082 抬到 0.188，暗部彻底消失。
3. 分带阈值 `0.30/0.62 → 0.24/0.52`（岛不是平的：20° 背光坡就已经落进中段）。

## 天空：一个坐标、一个频率、一个乘错的项
- **云一直是「撕开的白纸片」**，根因是三条叠加：
  1. `el * 0.20` 让一个格子约 1.4° 宽、0.7° 高，屏幕上 90×44 px —— 阈值切出来的就是格子本身。
     改 `0.40`，并把 `CloudScale` 提到 60。
  2. 值噪声是**可分离**的，等值线天然沿格线走。加了**域扭曲**（0.34 倍频、1.0 格位移）
     才把格线折成曲线。位移 1.6 格是过度（折成晶状薄片），1.0 才是「弯一下」。
  3. `lerp(cloudCol, sky*1.06, saturate(1-h*5)*0.55)` —— 画面上可见仰角只有 0..0.26，
     `h*5` 到 0.2 才归零，等于**整层云被掺了 25%–55% 的天空色**。改 `1-h*14` 收进 4° 以内。
- 掩膜改由低频场切：`nShape = (0.4n + 0.6·nLow/1.55 - 0.5)*2.0 + 0.5`。
  低八度定轮廓、高八度只进内部明暗；不乘 2.0 的那个版本覆盖率直接归零（方差被摊平了）。

## 树
- 树冠内侧的 `LeafDark → LeafMid` 垂直渐变**全部去掉**：相机在水面高度，看到的几乎全是裙边，
  于是每棵树都是「暗锥 + 亮边」= 遮阳伞。材质已经有真正的三档，两套明度系统只会打架。
- 冠半径 120+80 → 150+95、干高 85+70 → 95+80（岛才 29 m，原来每棵只有 8 px）。
- 冠的 `Height/Radius` 从 ~0.48 抬到 ~0.62：0.48 是荷叶，不是树冠。
