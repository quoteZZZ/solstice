# Solstice 手牌与出牌链路 · 界面评审

评审视角：八张牌摆在一条线上，能不能一眼判断「这是什么、能放哪、点了会发生什么」，以及每个动作有没有被回应。

## H01 · 拖到指定格这条路走不通（三段判定里的第一段永远抢不到）

- **界面**：拖影 / 拖放
- **触发场景**：按住任意手牌向上拖到世界里任意一格（0.42H、0.66H、正中央都试过）
- **现象**：`onDrag` 的分支顺序是「dy>90 回收 → dy<-40 随机 → overCanvas&&moved 指定落点」。手牌在屏幕底部，去世界上任何**看得见**的格子都必须向上 >40px，所以第二段永远先命中：拖到世界中央时 ghost 上的字是「松手释放（随机落点）」，`marks.clear()`、`setHover(null)`，没有任何落点高亮。第三段只在 `dy ∈ (-40, 0)` 时可达，而那一条 40px 高的窄带整个压在卡体上（卡体 751–967），拾到的是被手牌遮住的格子——实测在手牌上缘往上 5px 松手，会「看不见地」把牌放进 (2, 2) 并**直接消耗**（手牌 8→7 张）。也就是说：眼前这一步既不可达，可达的那一步是盲打。ghost 上常驻的说明还写着「拖到地面指定落点 · 向上随机 · 向下回收」，第一句是假的。
- **证据**：`mine-hand/10-drag-over.png`、`zoom-hand/drag-world-center.png`、`zoom-hand/drag-tiny-up.png`、`ui/hand.js:113-145`
- **严重度**：P0
- **建议**：把「指定落点」放到判定第一位（`overCanvas && moved` 先判，且用一个与手牌不重叠的阈值，例如 `clientY < handwrap.top`），`dy` 只用来决定「回收」；或直接改成「向上拖＝按光标落点，空格＝随机」。

## H02 · 向下拖 40–90px 不是「取消」，是**施卡**

- **界面**：拖影
- **触发场景**：想回收，从卡面往下拖 60px 后松手（没拖到底）
- **现象**：`dy ∈ (0, 90)` 时既不回收也不算 `idle`——因为画布铺满整屏、手牌区也在画布之上，`overCanvas` 成立，于是落进第三段 `cast`。实测：拖到 945px 处提示条变成「要放在已有地块上」（而不是「继续往下＝回收」），松手后弹出「要放在地块上 / 虚空承不住这张卡」。同一路径换成一张「土地」卡则不报错——它会在被手牌盖住的那一格**静默造出一片地并消耗掉这张牌**，手牌 8→8（补牌），屏幕上什么都没有发生。也就是说：玩家以为自己在「往回拖一点」，程序在「往看不见的地方打牌」。
- **证据**：`zoom-hand/probe2.json`（`drag_tiny-up.tip = 松手放在 (2, 2)`）、复现记录「向下 60px → tip=要放在已有地块上、cells 0→0、toast=要放在地块上」、`ui/hand.js:119-145`
- **严重度**：P1
- **建议**：把 `overCanvas` 的判定限制在 `clientY < handwrap.top`（手牌区上方才算世界），手牌区内一律回落到 `idle`/`recycle`；`idle` 松手给一句「已取消」。

## H03 · 拖影正好盖住要放的那一格，而且没有落点预览

- **界面**：拖影
- **触发场景**：把一张「土地」向上拖到世界中央
- **现象**：`#ghost` 是 `translate(-50%,-50%)`，129×205 的卡以光标为中心——光标所在的那格被卡面整个盖住，要放哪里全靠猜。同时 `mode=random` 时 `SOL.render.marks.clear()` + `setHover(null)`，世界里连一个高亮格、一条范围圈都没有（`mark` 层长度 0）。相比之下点世界施卡时 `hoverinfo` 会给「陆地 · (-2,-1)」，拖拽这条路径反而更少信息。
- **证据**：`mine-hand/10-drag-over.png`、`zoom-hand/drag-world-center.png`
- **严重度**：P1
- **建议**：ghost 改成「右下偏移」或只显示卡头 40px；拖拽期间保留 `setHover` + `marks`，哪怕落点是随机的也画出将要落的那一格。

## H04 · 拖影会重复挂载，最后半张卡永久钉在屏幕左上角

- **界面**：拖影
- **触发场景**：上一次拖拽没有 `pointerup`（指针移出窗口 / 两只手指 / 连续两次 pointerdown）时再按下另一张卡
- **现象**：`beginDrag` 没有「已有 drag 就先结束」的保护；`moveGhost` / `endDrag` 又都用 `getElementById('ghost')`，只认文档里的**第一个**。于是第二次按下会再 `createElement` 一个同 id 的节点，而 `moveGhost` 移动的是第一个（旧的那个），新的那个从未被定位，停在 `left:0;top:0`——正好是屏幕左上角，露出半张卡，压住 `SOLSTICE` 品牌字和左侧导航，`z-index:64` 又在所有面板之上。松手时 `endDrag` 只删掉第一个，留下这个钉死的残影。截图里它从 `11-drag-recycle` 一直挂到 `23-codex-detail` 都没消失，只有刷新能清掉。
- **证据**：`mine-hand/11-drag-recycle.png`、`mine-hand/12-dropped.png`、`mine-hand/16-pack-deal.png`、`mine-hand/23-codex-detail.png`、`zoom-hand/z11-tl.png`（左上角 3× 放大，可见半张「太阳」的「全图光 / 素 三 / 准温度 / 加一…」和「↩ —」）
- **严重度**：P1
- **建议**：`beginDrag` 开头 `if (drag) endDrag(null)`；ghost 用 `querySelectorAll('#ghost').forEach(el => el.remove())`，或干脆存元素引用而不是靠 id 查。

## H05 · 0 环卡：拖影说「松手回收」，松手说「不能回收」

- **界面**：拖影 → toast
- **触发场景**：对任意 0 环卡向下拖过 90px 松手
- **现象**：拖拽中 tip 是「松手回收（0 环不返还）」——一个明确的「可以做」的措辞；松手后 `S.recycle` 直接拒绝：「不能回收 / 0 环卡不返还时素」。55 张卡里 22 张 `tier===0`，且 0 环卡同时都是 `reclaim===0`，等于开局手里大概率一半以上是「拖下去必然报错」的牌。反向也不对：`card.reclaim ? … : '松手回收（0 环不返还）'` 用 reclaim 判断，文案却断言「0 环」，非 0 环但 reclaim 为 0 的卡会说错理由。
- **证据**：`mine-hand/11-drag-recycle.png` → `mine-hand/12-dropped.png`（toast 原文）、`sim/cast.js:138`、`sim/cast.js:116`
- **严重度**：P1
- **建议**：0 环卡的 tip 直接写「0 环卡不能回收」并把 ghost 置灰/禁用 `rec` 态；文案按 `card.tier===0` 而不是 `reclaim` 分支。

## H06 · 施卡成功没有任何反馈，新牌还插回同一个槽位

- **界面**：手牌
- **触发场景**：选中一张卡点世界施放（成功）
- **现象**：`UI.cast` 成功后不弹 toast；只有当 `res.gain` 存在时才有 `flyTo`。而 `S.consume(i)` 的补牌是 `splice(i, 0, 新卡)`——新抽的牌插在**被打出的那个下标**上。于是玩家看到的画面是：第 4 格原来是「土丘」，一眨眼还是第 4 格，但变成了「泥土」，琥珀选中环也还在第 4 格。整排没有任何位置变化、没有翻牌、没有闪光，「打出去一张」被读成「这张卡换了张脸」。对比 `mine-hand/06-toast-reject.png`（第 4 格=土丘）与 `mine-hand/08-click-cast.png`（第 4 格=泥土，仍选中）。
- **证据**：`mine-hand/06-toast-reject.png`、`mine-hand/08-click-cast.png`、`sim/cast.js:488-495`
- **严重度**：P1
- **建议**：补牌追加到末尾（或留 1 个空槽再合拢），并给「打出的那张」一个 150ms 的飞出/淡出，让「消失 → 补牌」两个动作分开。

## H07 · toast 停 5.2 秒、可叠 4 条，旧提示会被当成这次的结果

- **界面**：toast
- **触发场景**：先失败一次，2 秒内再做一次成功的操作
- **现象**：`setTimeout(…, 5200)`，最多同时挂 4 条，且不区分新旧。`mine-hand/08-click-cast.png` 里世界左下角已经长出了新陆地（说明施放成功），顶部却还挂着上一条「要放在地块上 / 虚空承不住这张卡」——任何人看这张图都会认为这次失败了。反过来 `mine-hand/09-click-cast-onland.png` 里只有同一条旧 toast、没有任何新提示，也无法判断这次到底做了什么。stress 场景连按 8 次，屏幕上变成 4 个一模一样的方框从 y=40 排到 y=230（`mine-hand-stress/26-stress-reject.png`），既不知道发生了几次，也不知道这次和上次是不是同一件事。
- **证据**：`mine-hand/08-click-cast.png`、`mine-hand/09-click-cast-onland.png`、`mine-hand-stress/26-stress-reject.png`
- **严重度**：P1
- **建议**：同文案去重（`if (上一条同样文字) 重置计时并做一次 1.2 倍的闪动，不新增一条`）；成功动作给一条正向 toast 把旧的反向提示顶掉；上限收到 2 条。

## H08 · 撤销按钮 51×22，5.2 秒后消失，而它是误回收的唯一挽回口

- **界面**：toast
- **触发场景**：回收一张可回收的卡（如「铜钟」4 环 / reclaim 2）
- **现象**：toast 尺寸 77×85（x=802, y=125），里面三行：`回收` / `+2 时素` / 一个按钮 `撤销`；按钮实测 `51 × 22px`、字号 12px。22px 高低于任何可点击下限（桌面 32、触屏 44），而且它只有 5.2 秒寿命、位置在屏幕正上方离手牌 600px 的地方。同一份代码里 `拖到 90px 以下就回收` 没有任何二次确认，误拖的代价与主动回收一样大。
- **证据**：`zoom-hand/toast-undo-real.png`、`zoom-hand/probe4.json`（`btn:{w:51,h:22}`）、`ui/hud.js:80-96`
- **严重度**：P1
- **建议**：撤销按钮做到 32px 高、加大到 toast 宽度；回收后 5 秒内允许 `Ctrl+Z`，别只靠这块小按钮。

## H09 · 图鉴详情把整卡缩到 0.86 倍，正文比手牌还小

- **界面**：卡库详情 / 手牌
- **触发场景**：图鉴点开「水」
- **现象**：详情外层是 `<div style="transform:scale(.86)">`，302×440 的整卡被渲染成 256×373：`fx` 13px → **11.2px**，`cond` 与 `num` 11px → **9.5px**，底栏 ATK/DEF 11px → **9.5px**，卡名 19px → 16.3px。而手牌版同一条效果句是 12px、单行 8 个字——**唯一一个「完整看」的界面，正文比「扫一眼」的界面还小**，条件行和数值行更是掉到 9.5px。同时这块详情卡底下还空着约 200px 面板高度，完全放得下 1:1。两套版式的字段也不一致：手牌上没有 `cond`、没有 `num`、没有 `ATK/DEF` 和编号。
- **证据**：`mine-hand/23-codex-detail.png`、`zoom-hand/z23-card.png`（3× 放大才读得顺）、`ui/panels.js:293`、实测 `.card 255.8×372.7 / fx 11.0px / cond 9.3px`
- **严重度**：P1
- **建议**：详情卡改 1:1（302×440）并让面板内部滚动，或至少在 0.86 的基础上去掉 `scale` 只缩插画——正文一律不低于 12px。

## H10 · 开局大半排是灰的，能打的那张只靠「亮一点」区分

- **界面**：手牌
- **触发场景**：刚进界、世界还是空的时候
- **现象**：`S.playable` 对非 land/sun/law 一律 false，所以第一手 8 张里通常 5–7 张带 `.cant`（`04-enter-empty` 这一手是 1 亮 7 灰）：正文 `#c3cedb → #8b98a6`（相对亮度 0.61 → 0.31，掉一半）、插画 `grayscale(.78) brightness(.7)`、环条点亮格变 `#5d666f`。灰化后的正文对底仍约 6.5:1，是**能读**的——所以「不能打」并不是靠读不清来传达，而是靠半个亮度差；大半排同时灰掉时，画面读成「这一手差不多全废了」，而能打的那张只是「没那么灰」。卡面上没有任何「为什么不能打」的字（是缺地块？缺植物？），只能去读效果句自己推。
- **证据**：`mine-hand/04-enter-empty.png`、`styles/card.css:172-183`
- **严重度**：P1
- **建议**：给可打卡一个正向信号（名带右侧一枚小圆点/一条 2px 顶边），灰卡在 `.hreq` 位置直接印出缺什么（「需地块」），别让玩家自己反推。

## H11 · 右下角第 4 个按钮是顶栏档位的重复控件，还用了同一串「1×」

- **界面**：手牌工具条（actbar）
- **触发场景**：任意时刻看右下
- **现象**：actbar 四个按钮是 `✦` / `↩` / `↻` / `1×`，第四个 `data-act="gear"` 调 `S.cmd.nextGear()`，标签直接取 `S.GEARS[gear].label`——也就是「暂停 / 0.5× / 1× / 2× / 4×」，和顶栏那个**同一组值**。同一个屏幕上因此有两个「1×」：顶栏的是时间倍速，右下的是「档位」，点哪一个都在改同一个状态。而且它 11px、混在三个图标按钮里，读起来像「这张卡是 1 倍」。
- **证据**：`mine-hand/04-enter-empty.png`（顶栏 0.5×/1×/2×/4× 与右下 1× 同屏）、`mine-hand-stress/26-stress-reject.png`
- **严重度**：P1
- **建议**：删掉 actbar 的 gear 按钮（顶栏已有），把位置让给「图鉴」或「手牌上限」；若必须保留，用「档」字或齿轮图标而不是倍速字符串。

## H12 · 重抽的梯价只写在 title 里，连抽三次后看不到下一次是 40

- **界面**：手牌工具条 / toast
- **触发场景**：连点 ↻ 三次（stress 场景）
- **现象**：按钮可见文字只有 `↻`，价格仅存在于 `title="重抽一手（5 时素 · R · 连抽翻倍）"`，要悬停 36×36 的图标才看得到；重抽本身不弹 toast，只写一行左栏日志「重抽一手 −5 时素」（4.6 秒后消失、最多 8 行）。连抽三次后 `rerollCost()` 已经是 40，界面上没有任何常驻位置写着这个数——玩家点下去之前不知道要花 40。另外日志行用 `−`（U+2212），别处日志用 `-`。
- **证据**：`mine-hand-stress/28-stress-recycle.png`（左栏三行「重抽一手 −5 / −10 / −20 时素」）、`zoom-hand/probe4.json`（`before.title` 5 / `after.title` 10）
- **严重度**：P1
- **建议**：↻ 按钮上直接印当前价（`↻ 5`、`↻ 10`、`↻ 40`），或价差时把按钮换成琥珀色并加一条「下一手 40」。

## H13 · 效果句上限 4 行：一张被截，四行的卡最后一行被渐隐压住

- **界面**：手牌卡面
- **触发场景**：手里出现「太阳」（35 字）
- **现象**：说明块内容高 72px（4×18），`-webkit-line-clamp:4`。「太阳」需要 5 行（`scrollHeight 90`），第 4 行以省略号收尾，读成「+0.5（只加一…」，句子断在「一次）。」之前。更普遍的问题是 4 行卡的**第 4 行**：`.hsum:after` 是从底边往上 10px 的渐隐，而文字正好写到 76px 处（块高 80、上内边距 4），也就是每一张 4 行卡（本次实测「鹰」「狼」，前一手是「猴」「鹿」「铁杉」）的最后一行下半截都盖在同一条黑渐变下面，看着像「被切了一半」。3 行卡则有 16px 的纯空底。
- **证据**：`zoom-hand/sun-4x.png`（「+0.5 （只加一…」）、`zoom-hand/z-card-bottom.png`、`zoom-hand/probe.json`（`太阳 sh=90 ch=72 cut=true`）
- **严重度**：P1
- **建议**：渐隐改成「只在真截断时出现」（JS 判 `scrollHeight>clientHeight` 再挂 class），高度按行数自适应（`min-height` 72 + 最多 90），别让固定 80 同时承担 3 行和 4 行。

## H14 · 卡内三段竖向间距是 5 / 3 / 4，三种都不一样（像素）

- **界面**：手牌卡面（像素）
- **触发场景**：竖着量任意一张手牌的分隔
- **现象**：实测各块位置：画芯 `45–102`、说明块 `107–187`、底栏 `190–210`、卡内容底 `214`。三个间隔分别是 **5 / 3 / 4px**。更要紧的是，每个分界其实由**两条** 1px 线夹着这段空隙构成：画芯底边 `rgba(el,.28)` + 说明块顶边 `rgba(el,.12)`、说明块底边 `.12` + 底栏顶边 `.055`——六条线三种浓度三种间距，放大后是一组读不出规律的横线。`card.css` 顶部注释写的高度预算是「说明 6+74 / 底栏 4+20+5」，与实际（80 / 3+20+4）已经差了 7px，画芯因此只剩 57 而不是注释说的 60——预算表本身也失效了。
- **证据**：`zoom-hand/card-single.png`、`zoom-hand/probe-layout.json`（`win 45..102`、`sum 107..187`、`foot 190..210`）、`styles/card.css:105-107`
- **严重度**：P2
- **建议**：把三段间距统一到 4px（说明块 `margin:4px 6px 0`、底栏 `margin:4px 6px`），并让注释里的预算跟着改，或直接删掉那段手算。

## H15 · 一张卡上有四个不同的左边线（0 / 6 / 8 / 16px）

- **界面**：手牌卡面（像素）
- **触发场景**：竖着看任意一张手牌

## H19 · 中线两张卡的 z-index 打平，叠压方向靠 DOM 顺序决定（疑似）

- **界面**：手牌扇面（像素）
