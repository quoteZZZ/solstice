# 原型 → 正式开发：衔接评估（2026-11-04）

> 评估对象是仓库现状，不是设想。每条判断都带可核对的数字或文件。
> 结论先说，证据在后；引擎选型单列一节，因为它牵动其余所有事。

---

## §0 结论

**三句话：**

1. **技术栈只规划了一半**——`TECH.md` §3 给出了 `game/` 的目录与五条硬约束（这是好的，
   硬约束是真正可执行的），但**没有构建工具、没有语言选型、没有资产管线、没有存档格式、没有性能预算**。
   它描述的是「同一个 Web 原型的更整洁版本」，不是「正式开发的工程」。
2. **基础资料里最缺的不是文档，是资产与产能**——文档 16 份、代码 6.2k 行、四个回归都在；
   但**音频 0 个、位图 0 张、字体 0 个、卡池 55/540、图鉴 6/60**，且卡面美术是运行时用 canvas
   现画的（`render/grid.js` 的 `standeeTex`），不是资产。这意味着「换引擎」等于美术从零开始。
3. **现在不该上 UE5**，也不该把「选引擎」当成下一件事。理由不是 UE 不好，是当前形态用不上它：
   纸片剧场 + 方块地形 + 卡牌文本为主，UE 的强项（PBR、Niagara、后处理）在这里全是空转，
   而它的成本（C++/蓝图双栈、编译迭代、单人学习曲线、本机未安装）立刻要付。
   **而且 `CHARTER.md` §4.1「已否决」里明确列着「UE5 模拟沙盒」**——要改回去，得先按 §5 变更纪律改立项。

**建议的下一步不是选引擎，是两道闸：**先做工程转正（2 周），再做垂直切片（4–6 周），
切片跑通之后再拿真实数据决定要不要换引擎。届时判断依据见 §4.4。

## §3 流程与推进顺序：五个可优化的地方

### 3.1 现在是在「没有资产、没有存档、没有音效」的状态下打磨 UI

`REVIEW-UI-2026-11-04.md` 记了 178 条问题，其中相当一部分（卡面画芯、立牌重复、地面圆环）
会在美术资产到位后**自动消失或完全改写**。反过来，「反馈方向是反的」（成功没反馈、失败有 toast）
这类问题才是资产来了也还在的真问题。

**建议：把 178 条分成「与资产无关」和「等资产」两堆，只修前一堆。** 这一条能省掉大量返工。

### 3.2 内容产能是主矛盾，但流程还停在「手改代码」

`FILL.md` 写得很好，但它假设的是「一个人一张张加」。55 → 540 是 **×9.8**，图鉴 6 → 60 是 **×10**。

更麻烦的是：**现在没有任何产能数据。** git 里 `data/cards.matter.js` 只有 4 次提交（都在 11-03/04），
看不出「一张卡从想到验完要多久」。没有单卡成本，就排不出 540 张的期——
这是比「缺工具」更前置的一个缺口（记为 G14）。

**建议：G5（录入工具）优先级提到 G3 之前。** 工具先行是内容型项目唯一被反复验证过的顺序。

### 3.3 没有「垂直切片」这一步，直接在想正式开发

现在的产物是**原型**（能跑、能验机制），不是**切片**（能给别人玩并给出反馈）。
两者差的是：存档、音效、开场引导、性能稳定、以及「15 分钟内有变化」的节奏设计。

**建议：M1 = 垂直切片**，验收标准写死（G7），在此之前不谈引擎。

### 3.4 引擎决策的时机错了

「先选引擎再开工」在这里是错的顺序，因为它会绑死切片的方向。
正确顺序是：**切片用最便宜的方式做（现有 Web），拿切片的真实数据（格数、draw call、帧时间、内容量）
去回答「Web 还撑不撑得住」**，再决定是否迁移。§4.4 给了触发条件。

### 3.5 测试偏科，但偏得对

sim 有确定性回归（`digest` 同种子重演），UI 只有冒烟 + 刚加的几何断言。
这个偏法其实是对的——因为 **sim 是唯一跨引擎可复用的部分**，它测得越死，将来迁移越安全。
要继续加固的是 sim，不是 UI 像素。

## §4 引擎选型

### 4.1 先看这个项目到底需要渲染什么

| 需求 | 现状 | 对引擎的要求 |
|---|---|---|
| 方块地形，目标 1 万格 | 实测 4761 格 = 1065 draw call | 需要实例化合批；Web 用 InstancedMesh 可解，引擎侧 ISM/MultiMesh 是标配 |
| 立牌（纸片） | 2D billboard，5 种形状 × 30 色 × 3 变体 | **不需要骨骼动画、不需要 PBR** |
| 光照 | 三盏灯 + 顶点色烘焙，无实时阴影（地形已退出 shadow pass） | 需求极低 |
| 卡牌 UI | 540 张卡面 + 图鉴 + 手牌 + 6 个面板，文本密集 | **这是最大的 UI 工作量**，DOM 是天然强项 |
| 动画 | 相机缓动、立牌摆动、落点扩散、新格弹起 | 全手写即可，不需要动画状态机 |
| 物理 | 无 | 不需要 |
| 联机 | 无（CHARTER §3.3 非目标） | 不需要 |
| 平台 | PC 为主 | — |

**结论：这个项目的技术需求重心在「数据 + UI + 大规模实例化」，不在「渲染质量」。**
这直接决定了选型的权重。

### 4.2 四个选项的对照

| 维度（按本项目权重排） | Web / three.js | Godot 4 | UE5 | Unity 6 |
|---|---|---|---|---|
| 现有 6.2k 行代码复用 | **100%** | 仅 `sim/` 1381 行可搬 | 仅 `sim/` 可搬（C++ 重写） | 仅 `sim/` 可搬（C# 重写） |
| 540 张卡的 UI 产能 | **优**（HTML/CSS，已有一整套） | 中（Control 节点，可做但不快） | **差**（UMG，540 张卡面是苦工） | 中（UGUI） |
| 纸片剧场风格契合 | **优**（已经做出来了） | 优（2D/3D 混合自然） | 中（要主动压平 PBR，容易越做越"重"） | 中 |
| 1 万格规模余量 | 中（需 InstancedMesh；再往上要考虑 WebGPU） | **优**（MultiMesh） | **优**（ISM） | 优 |
| 单人 + AI 的迭代速度 | **优**（改完刷新，无编译） | 优（编辑器快） | **差**（C++/蓝图双栈，本机 UBT 有坑史） | 中 |
| 本机能否今天开工 | **能**（Node 22 已装） | 否（需装 ~100MB） | 否（需 ~100GB + VS + 引擎，本机检测无 UE） | 否 |
| 分发 | 中（网页/itch 容易；Steam 要套壳） | **优**（直出多平台） | 优 | 优 |
| 授权成本 | 0 | 0（MIT） | 超过 100 万美元后 5% 分成 | 订阅制，政策有变更史 |
| 主要风险 | 规模上限、无编辑器、资产管线自建 | 生态与中间件弱、社区小 | **过重**：为一个纸片游戏付 3D 引擎的全部成本 | 政策不确定、同样偏重 |

### 4.3 三种典型场景下该怎么选

- **只想把 Solstice 做成「可玩的独立作品」，1–2 人，PC，风格化** → **Web 继续做**，需要时套 Electron/Tauri 上 Steam。
  理由：这个游戏的卖点是「世界自己运转」和「卡与卡的因果」，不是画面。为画面付引擎成本是错配。
- **确定要上 Steam，且要 3D 光照/粒子/后处理当卖点，团队 ≥3 人** → **Godot 4 优先，UE5 次之**。
  Godot 的 MultiMesh + 轻量工作流更贴合「大量小物件 + 风格化」；UE5 只有在需要 Nanite/Lumen 级别表现时才值得。
- **要做 3A 级演示或需要成熟商业中间件（音频、过场、主机移植）** → **UE5**。这一档与当前项目规模不匹配。

### 4.4 什么时候该重新评估引擎（触发条件）

出现**任意两条**再启动迁移评估，否则不动：

1. 目标格数 > 2 万，且 Web 侧合批后 1080p 仍无法稳定 60fps；
2. 需要实时阴影/体积光/粒子特效作为**卖点**（不是"更好看一点"）；
3. 确定上 Steam 且要做成就/云存档/手柄/多语言商店页；
4. 有第二个人能专职做美术/技术美术。

### 4.5 与立项文档的冲突（需要拍板）

`CHARTER.md` §4.1「已否决」第 6 项写着 **「UE5 模拟沙盒」**，理由与其余五项并列为「形态被清除」。
按 §5 变更纪律：**改支柱或推翻否决项，必须先改 CHARTER，再改域文档，最后才动工程。**

所以「要不要用 UE5」不是一个纯技术问题——它是**要推翻一条已写死的否决**。
建议先回答一个问题：当初否决 UE5 的理由（太重 / 与三人团队不匹配），今天变了吗？
如果没变，本文 §4.3 的结论就是「继续 Web」；如果变了（比如拿到美术资源或团队扩到 3 人），
那就先改 CHARTER §4.1，再谈工程。

## §5 建议的衔接方案

### 阶段 0：补齐决策前提（1 周）

- 写 `specs/ART.md`（G1）与 `assets/` 规范（G2）；
- 拍板语言与构建（G3），同次改 `TECH.md` §1「为什么不是 ES module」——那条约束只对原型成立；
- 定性能预算（G6）与垂直切片验收（G7）。

**闸口：这三份文档没落地，不开工。**

### 阶段 1：工程转正（2 周）

- Vite + ES module +（TS 或 JSDoc 类型）；`sim/` 保持零依赖、四条回归原样跑通；
- 目录按 `TECH.md` §3 落地，但 `assets/` 从"空目录名"变成真要放东西的地方；
- CI 扩到跑 `review-run` 的缩水版（3 场景），保住"改完能自己验"这条能力；
- **验收：`npm run dev` 一条命令起来，四条回归 + docs-check 全绿。**

### 阶段 2：垂直切片（4–6 周）

- 20 张卡（从现有 55 里挑最能体现因果链的）走通：资产 → 数据 → 卡面 → 施卡 → 存档 → 读档；
- 加 8 类音效（G8）、开场 15 分钟节奏、设置面板接线；
- 打包一个「能发给别人玩」的版本。

**闸口：拿切片实测数据（格数 / draw call / 帧时间 / 内容量 / 玩家反馈）回答 §4.4，再决定引擎。**

### 阶段 3：内容量产（12 周+）

- 先上录入工具（G5），再把卡池推到 200；
- 图鉴 6 → 20；
- 每 50 张卡做一次 `npm run cards` + `codex` + 全量 `review-run` 回归。

## §6 一句话建议

**别在这时候选引擎。** 先花一周把美术规范、资产管线、构建选型三件事写死，
再花两周把工程转正，然后用一个能发给别人玩的垂直切片，去换「要不要上引擎」这个问题的真实答案。
现在做引擎对比，比的是纸面参数；切片之后做，比的是你的项目。
