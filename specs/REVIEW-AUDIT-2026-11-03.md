# 评审运行复盘 · 第一轮六角色（2026-11-03）

> 这份文件评的是**评审机制本身**（那轮跑得怎么样），不评 Solstice。
> 评 Solstice 的结论在 [REVIEW-2026-11-03.md](REVIEW-2026-11-03.md)。
> 分成两份写，是因为一份要改**机制**、一份要改**项目**；混在一起会让「裁决」和「复盘」互相污染——
> 而这正好是本轮暴露的问题之一（见 P0-1）。

## 0 这份复盘凭什么说别人

复盘有两种证据，只有第二种能当依据：

| 证据 | 来源 | 够不够 |
|---|---|---|
| E1 评审原文 | `REVIEW-2026-11-03.md` 的表格与行号（本文件每处引用都可 `grep` 复现） | 够证明"它当时写了什么" |
| **E2 实装结果** | 那轮的 5 条 P0 + 2 条 P1 已全部落进代码并跑通（`npm run det` / `npm run codex` / `npm test` 全绿，提交 `0ac8322`，22 文件 +922/−97） | **够证明"它当时说得对不对"** |

只有做完一遍才知道哪句说对了。这是复盘唯一比评审本身强的地方，也是它诚实的边界：
**没实装的部分，本文件同样只能给判断，不给结论。**

## 2 各角色表现

**先定尺子**（不然又是一堆形容词）：

| 指标 | 定义 | 为什么单列 |
|---|---|---|
| 命中 | 实装阶段被证实成立的比例 | 意见质量 |
| 独占 | 只有这个角色会提的条数 | 角色设计有没有必要 |
| **改变** | 最终落成动作的条数 | **命中数 ≠ 影响力**：R5 命中 6 条却只折成 1 个动作 |
| 越界 | 超出本角色判据的条数 | 职责有没有守住 |

| 角色 | 条 | 命中 | 独占 | 改变 | 越界 | 评分 |
|---|---|---|---|---|---|---|
| R1 产品 | 3 | 2/3 | 1 | 1（图鉴 6 条） | 0 | ★★★☆ |
| R2 用户 | 3 | 3/3 | 1 | 2（A4 / A5，A1 联署） | 0 | ★★★★★ |
| R3 审计 | 3 | 2/3 | 1 | 2（A3 / A8） | **2** | ★★☆☆ |

### R1 产品经理 ★★★☆

找准了唯一的软目标（图鉴 0 条），而且它判断对了「扩池不是瓶颈」——这一条后来被 §4.5 直接采纳成否决项。
**缺陷**：1.2 是判断不是发现，证据列写的是「STATUS §3.1；卡库有，合成树未实装」，两处都支撑不了结论。
**判词**：唯一一个站在"三个月后还有没有人玩"这个尺度上看问题的人，但顺手写了一条没法证伪的意见。

### R2 终端用户 ★★★★★

本轮性价比最高的角色。它是**唯一真的去点"复制坐标"的人**——三个 P0 里两个由它起头（坐标不是种子 / 特征 `init` 与虚无开局打架）。
2.1 的证据写得极准（`creator.js:11-13` 全用 `Math.random`、`:23` 的 seed 只用于显示、`:366` 传给 sim 后无人使用），
实装时一行没错。
**缺陷**：2.2（掷骰只影响剖面图）与 R6-6.2（剖面图与结算无关）是同一件事；**全篇没有一条外部体验基线**
（WorldBox / Terra Nil 的第 30 秒是怎么给的），所谓"用户"其实仍是读代码的工程师。
**判词**：最好的一次"假装不是开发者"。

### R3 安全与合规审计 ★★☆☆

**本轮最差的一次角色履行。** 它手里有否决权，需要它做的是**逐条对照 CHARTER §3 的五个非目标**
（无失败判定 / 时间不进卡池 / 不做引擎 / 不做服务端 / 不做账号）打勾或打叉；实际做的是：
4 条里 3 条投给了工程质量（第二时钟、注释矛盾、随机源），真正属于合规的那条只用一行
「没有踩红线」带过，且没有逐条对照。

| 它该做的 | 它实际做的 |
|---|---|
| 五个非目标逐条 → 通过 / 触碰 / 证据 | 一句"没有踩红线" |
| 否决权只用于红线 | 用在了 P0（工程）上 |

它提的 3.1 是真的、也确实该修，但那是 R4 的题。独占发现只剩 1 条：3.2（两处注释给两个值）——
这是全篇唯一一条纯"人祸"记录，别人不会去比对注释。
**判词**：有权力的人去做了别人的活，于是没人做自己的活；靠一条注释比对保住了席位。

### R4 运维工程师 ★★★★

P0 的根因是它给的（3 处 `Math.random` + `resetWorld` 不播种），而且它给了可执行的验收方式
（`npm run det` → `PASS`），这在 22 条里是唯一一条自带验证脚本的建议。**改变数最高（4 个动作）**。
**缺陷**：4.4（调试口只在控制台，CI 够不着）提了、成立了，但没进队列——它自己也没坚持。
**判词**：唯一一个把"怎么证明修好了"顺手写出来的人。

### R5 系统架构 ★★★★★

**命中率 100%（6/6）**，而且抓到了最难发现的一类问题：5.6「STATUS 把金属富集列为已接线，
但 `W.effects.metal` 写入后无人读取」—— 这不是 bug，是**文档比现实乐观**，靠读代码读不出来，要靠对照。
**缺陷**：① 6 条命中被折成 1 个动作（A7），影响力被条数低估；② 全篇证据用行号，而它自己
5.5 就证明了小节号会重复——引用体系在最需要它的那一次失效（P2-11）；
③ 它在评审里最能识别"一处地方两个事实"，但 §4.2 分歧清单里那处矛盾（图鉴 6 条 vs 60 条）
就是在它的成果旁边长出来的（P0-1）。
**判词**：查得最准的人，没被要求查自己。

### R6 视觉总监 ★★★☆

6.3「一屏之内两套真假标准」（剖面图 10 条特征都画，右栏只注明 4 条生效）是本轮最有画面感的一条，
改法也轻（加 `wired` 标）。6.1（卡面三档只对了两档）是事实，但它自己给的结论是"排 P2"——
一个"版式最大尺寸没验过"的结论被它自己降级了。
**缺陷**：6.2 与 R2-2.2 重复；对"没验完就不许定标"没给出硬结论。
**判词**：看得很准，但愿意为审美问题让路。

### 2.1 一个反直觉的结论：六个角色都别删

| 如果删掉 | 会丢掉什么 |
|---|---|
| R1 | 图鉴（唯一的软目标）——没人会从"三个月后还有没有人玩"看 |
| R2 | 复制坐标去复现的那一下（两个 P0 起头） |
| R3 | 注释矛盾（3.2）——这是唯一一条纯"人祸"记录 |
| R4 | 确定性回归脚本本身 |
| R5 | 6 条口径冲突 + 死字段 |
| R6 | 一屏两套真假标准 |

**每个角色至少有一条独占发现**。所以问题不在"要不要 6 个角色"，在"6 个之间怎么去重、怎么分工"（P0-3 / P0-5）。

## 4 改进建议（v2 机制补丁）

每条对应上面的编号。格式：**改哪 → 怎么改 → 怎么验**。

### P0-1 输出自洽：加一道 S5 自洽闸

- **改哪**：输出契约（机制稿 §5）＋ 收尾流程
- **怎么改**：交付前机械跑三条检查
  1. **一个决策点只允许一个结论**：全文搜同一术语（图鉴 / 昼夜 / 卡数），命中处必须状态一致；`已裁决 / 未决 / 已否决 / 已完成` 四态互斥
  2. **队列里每一项都能追溯唯一一条裁决**：P 级项没有对应裁决行 → 打回
  3. **被判"不动"的项不得出现在待办里**
- **怎么验**：把这三条写成一个 `check-review.py`（20 行就够），对 `REVIEW-*.md` 跑一遍输出 0 条冲突。**用 R5 查别人的尺子查自己。**

### P0-2 判据可执行：判据的交付物是脚本，不是一句话

- **改哪**：S4 质量闸 ＋ 任何"新增判定逻辑"的建议（图鉴 / 成就 / 事件触发条件）
- **怎么改**：一条判据进队列的前提是**能给出两条脚本**：一条点亮它、一条证明它不该点亮。
  写不出脚本的，降级为"提案"（不排期、不进 P 级）。
  本轮 `tests/codex.js` 就是模板：14 条断言 = 6 条正例 + 3 条反例 + 换界 + 阈值边界。
- **怎么验**：队列里每条判据都带一行 `npm run <脚本>` 与期望输出。

### P0-3 证据分级：E2 重新定义为"跑出来的"

- **改哪**：机制稿 §3 证据等级定义
- **怎么改**：
  | 级 | 含义 | 允许的形式 |
  |---|---|---|
  | E1 | 文档 / 代码原文 | 引用 + 小节号（不是行号） |
  | **E1.5** | **读代码得出的推断**（本轮的"E2"实际都是这一级） | 代码片段 + 一句推理 |
  | E2 | **真跑出来的** | 脚本输出 / 截图 / `digest` / 控制台日志 |
  | E3 | 外部检索 | 出处链接 |
  规矩：**E1.5 不得写成 E2**；一条评审里 E2 为 0 时，必须在结论第一行标注「本轮无实测」。
- **还要修一件**：六个角色的意见表必须**列结构相同**（`# / 意见 / 证据级 + 锚 / 风险`）。
  本轮 R5 换了列，导致它 6 条全真的发现一条证据等级都没带上——**表结构不一致 = 数据静默丢失**。
- **怎么验**：文件头统计一行 `E1 x / E1.5 y / E2 z / E3 w`，由脚本数，不靠人写；每张意见表列数一致。

### P0-4 去重：S2 之后插一道「根因折叠」

- **改哪**：流水线 S2 → S3 之间
- **怎么改**：先折叠再质询。产出「根因 → 涉及意见编号」表；折叠比 < 2:1 不许进 S3。
  被并的意见降为**附议**（保留编号，不再单独占一行）。
- **怎么验**：S3 的输入必须是折叠后的根因表；输出里的每一条都能反查到 ≥1 个意见编号。
  本轮就是 22 → 7，折叠比 3.1:1。

### P0-5 否决权：只用于红线，且必须逐条

- **改哪**：R3 角色模板
- **怎么改**：输出固定为两段——
  1. **红线表**：CHARTER §3 的五个非目标逐条 → `通过 / 触碰 / 证据`（五条都写，不许省略）
  2. **普通意见**：以普通角色身份提交，**不带否决标签**
  否决权只在第 1 段出现"触碰"时行使。
- **怎么验**：R3 的输出里，红线表必须恰好 5 行；非红线意见不得出现"否决"字样。

### P1-6 意见 → 动作闭环

- **改哪**：输出契约的动作表
- **怎么改**：每条意见强制带一列「承接」：`A<n>` 或 `拒绝 + 一句理由`。空着不许交付。
- **怎么验**：`意见条数 == 有承接的条数`，脚本校验。

### P1-7 动作锚：锚必须由脚本验存在，且验语义

- **改哪**：动作表
- **怎么改**：每行加「目标锚」列，形如 `specs/SETTING.md#§1.6`；交付前对每个锚跑一次
  `grep -n "^#\+ *§\?1\.6" <file>`，**0 命中打回**。
  光验存在不够（A7 的错误是锚存在但指错内容），所以锚还必须带**锚内首句片段**（如 `#§1.6 创世特征`），
  由脚本比对片段是否出现在该小节标题里。
- **怎么验**：锚检查 0 失败。

### P1-8 成本：每个 P 级项标行数

- **改哪**：优先级队列表
- **怎么改**：加「估行数 / 涉及文件数」两列；单轮总预算建议 ≤ 300 行 / ≤ 8 文件，
  超了必须拆轮（本轮 922 行 / 22 文件 = 三轮的量，一轮吃掉了）。
- **怎么验**：队列底部自动求和；超过预算则不能标"本轮"。

### P1-9 分歧：质询表加「保留意见」列

- **改哪**：交叉质询表
- **怎么改**：每一行强制填「保留意见」（哪怕"无"）；`审美级 / 立项级` 的争议**不允许角色之间互相说服结案**，
  必须升级为用户裁决（本轮 Q2 的"折中采纳"就是越权：折中方案是设计决定，不是评审决定）。
- **怎么验**：保留意见列非空率 100%；升级项在 §4.2 有对应行。

### P1-10 判据隔离：至少两个角色必须带外部对照

- **改哪**：角色模板
- **怎么改**：R2（用户）与 R6（视觉）各强制给 ≥1 条 E3（竞品 / 通行做法 / 权威规范），
  并写"我们的做法与之差在哪"。其余角色可引用内部证据，但**不得把 E1 当成 E3 用**。
- **怎么验**：E3 ≥ 2 条，且分属两个角色。

### P2-11 引用：结构化锚 + 原文片段，行号只作辅助

- **改哪**：证据列写法
- **怎么改**：证据写成 `文件#小节 → 原文片段`（如 `SETTING#§1.6 → 「创世特征：乘数，不是地形」`），
  或直接给一段 `grep` 命令。行号可留，但**不得单独使用**。
- **怎么验**：随机抽 5 条证据，按锚能在 10 秒内定位。
